# Decision Log

Append concise implementation/product decisions that do not warrant their own ADR. Do not rewrite history; add dated entries.

## Initial decisions

- Project working title: **Project Saturday**.
- Player perspective, not coach/dynasty perspective.
- Weekly loop with approximately three player-selected actions.
- Skill-card system is a headline mechanic.
- Vertical slice begins with WR.
- Fictional composite programs, not licensed or 1:1 renamed real schools.
- Korean and English are simultaneous first-class locales.
- Persistent alumni/legacy system expands options/history more than raw power.
- Web/PWA and deterministic pure TypeScript game core.

## 2026-08-30

- M0 is executed as one integration plan with independently owned core, content, and web work streams; the primary agent owns root tooling and final integration.
- Missing git metadata is treated as an environment limitation, not a delivery blocker; durable docs and verified files remain the checkpoint mechanism.
- The M0 toolchain pins pnpm 11.24 on Node 22, Vite/Vitest's current supported runtime. TypeScript 6.0 is pinned instead of TypeScript 7 because the current `typescript-eslint` peer contract is `<6.1`.
- Locale messages use ICU syntax end to end; `game-content` validates ICU contracts and the React app will use the corresponding i18next ICU runtime rather than maintaining two interpolation dialects.
- pnpm's dependency-script allowlist permits only `sharp` during M0, at its lockfile-pinned transitive version, because the PWA asset generator needs it to produce installable PNG icons. Unreviewed future dependency scripts remain denied by default.
- The deterministic RNG uses immutable, versioned xoshiro128** state. Seeded scenario failures include the scenario ID, seed, and reproduction string; built packages export emitted `dist` modules by default while Vite/tests opt into an explicit `source` condition.
- M0 browser persistence uses the five planned IndexedDB stores behind a typed adapter. Memory fallback remains playable but is visibly announced in both locales so ephemeral progress is never presented as durable.
- Shipping browser source, browser tests, and Node-based Vite tooling have separate TypeScript contexts. A compile guard fails if Node globals leak into production browser source.
- User-visible copy enforcement combines ICU catalog contract validation with a TypeScript AST/data-flow check for shipping `.ts`/`.tsx`; indirect JSX, visible DOM, attribute, and dialog literals are covered by negative fixtures.
- The PWA uses prompt-based updates and generated original install assets. Production verification imports emitted workspace packages, validates shipped content, and rejects duplicate icon/manifest service-worker precache entries.
- Playwright serves the already-built app from an in-process global-setup HTTP server. This keeps the offline tests production-representative and makes teardown deterministic on Windows.
- Shipped gameplay/content IDs retain the documented lower-snake-case namespace convention (`archetype_wr_*`, `background_*`, `personality_*`). A cross-package contract test prevents controlled creation IDs and attribute/state IDs from drifting between core and content.

## 2026-08-31

- `CareerRun` schema v1 stores a pre-program WR, explicit career seed, unconsumed serialized RNG state, and zero-based development `weekIndex`; `programId` is `null` until M3 introduces recruiting through a migration.
- Player IDs are derived only from the immutable career seed with a distinct domain separator. Creation edits cannot change identity; the career/player namespaces prevent the two deterministic IDs from colliding.
- Personality incompatibility is authoritative core mechanics, not trusted caller data. Raw CareerRun validation and content contract tests enforce the same symmetric pair map.
- Overall is a rounded equal-weight view across the 16 current WR attributes and is never saved or directly trained. Future role/depth evaluation weights remain separate M3 mechanics.
- Development weeks use the persisted `PLAN_ACTIONS` -> `RESOLVE_ACTIONS` -> `WEEK_END` phase sequence. Committing a three-slot queue, resolving each action, and advancing a week are separate immutable revisions so web persistence can checkpoint every committed transition without saving UI drafts.
- M1 development tuning is content-owned and fixed-point: Body efficiency is `600 + 4 * Body` permille, passive week recovery is 10, and proficiency thresholds/multipliers are `[0,2,5,9,14,20]` / `[1000,1080,1140,1180,1210,1230]`. Core validates monotonic thresholds and strictly diminishing multiplier gains instead of embedding designer values.
- Weekly content separates localized presentation/eligibility metadata from strict mechanical projections. Every action has explicit position requirements and query tags, while `game-core` receives only stable IDs and numeric effects.
- M1 appearance is persisted identity with no mechanical modifiers. The content package owns 51 bilingual cosmetic choices and practical metric WR measurement options; one creation helper projects selected stable mechanical IDs into strict core input without leaking presentation data into rules.
- The checked-in M1 development report is pinned to content compatibility version 1 and derives 72 careers from 24 reproduction seeds. Scenario runners use only public core commands, can JSON-round-trip after every transition, validate every resulting CareerRun, and assert that deterministic M1 actions consume no RNG draws.
- Career saves use canonical JSON plus an FNV-1a checksum over the version, content version, timestamps, and full payload. Each committed transition writes a uniquely identified snapshot before current state; caller-owned input is cloned synchronously, and storage-level exclusive locking prevents same-revision branches from silently winning.
- Recovery ranks all compatible careers by globally monotonic save timestamp, with revision and current-save preference only as deterministic tie-breakers. Creating a different career is an explicit replacement operation so normal autosave cannot overwrite another, unreadable, future-version, or content-incompatible active save.
- Snapshot retention counts only valid compatible saves toward the rolling limit of 30. Corrupt entries are pruned, while future-version and content-incompatible snapshots are preserved outside that limit to avoid destructive downgrade behavior.
- The M1 web flow renders one decision surface per authoritative phase. Its ordered three-slot draft is React-local and never persisted; commit, each resolution, and week advance optimistically render the immutable core result but block subsequent commands until the corresponding save succeeds or is retried/reloaded.
- Creation and profile displays store only integer centimeters/kilograms. Korean edits/displays cm/kg; English edits/displays feet/inches and pounds through tested pure conversion helpers, so changing locale never changes CareerRun schema or adds a unit preference migration.
- M1 intentionally omits opponent, program, depth, injury, and game placeholders even though later UX context calls for them. The home surface shows only shipped state and commands: player identity, derived overall, week, Body, GPA, remaining actions, actual core results, and collapsed profile detail.
- M1 production E2E reads the native IndexedDB current-career envelope and polls exact phase/revision contracts instead of sleeping or inferring save completion from presentation. Locale cases are multiplied by the mobile/desktop projects; a separate true-320 px keyboard path checks element bounds and minimum primary target sizes, while the PWA smoke resumes an actual saved career offline.
- M1 phase and result changes move focus to a stable heading or atomic live-status region. Save failures always focus the remounted alert, successful retry restores the phase heading, and locale presentation/provider synchronization is immediate while only settings persistence is serialized and latest-request coalesced.
- M2 advances both the domain `CareerRun` schema and checksum envelope to version 2. Browser persistence recognizes only the verified legacy `(save 1, content 1, career 1)` tuple, checks its original checksum before pure core migration, and preserves unknown future versions. Additive skill content remains compatibility version 1, so the checked-in M1 baseline retains its historical compatibility identity.
- Until game/post-game rewards arrive, M2 uses a tuneable development breakthrough cadence after completed weeks 1, 5, 9, 13, and so on. Offers remain an authoritative persisted phase; later trigger replacement must preserve deterministic offer/acquisition semantics through migration.
- M2 uses four compact equipped slots, first-open-slot auto-equip for newly acquired cards, and planning-only loadout edits. A full loadout is never silently replaced.
- M2 derives owned inventory from an immutable acquisition log that records each offer, selection, week, and RNG draw range; it stores exactly four dense nullable equipment slots and only the six most recent action IDs for behavior weighting.
- M2 skill percentages use integer permille and additive stacking around 1000, with one final rounding step and bounded aggregate floors/caps. Applied action evidence is ordered by equipped slot then authored effect index; weekly results preserve base and modified values, and the latest passive recovery persists its completed week, before/after Body, requested/actual delta, and historical traces across reload and later loadout edits.
- The first M2 catalog contains 18 original WR-compatible cards in a 4 Development / 3 Game Day / 4 Body / 4 Mindset / 3 Life split. Base offer weights are C 100, B 70, A 35, and S 10; matching behavior adds 20% of that grade's base weight per counted affinity occurrence so behavior changes likelihood without erasing rarity. Nine cards carry mechanically validated tradeoffs, and declarative game hooks use hook-specific integer bounds until M4 resolves them.
- M2 breakthrough weights count each authored action tag once per matching entry in the six-action history. Repetition counts occurrences beyond each action ID's first, variety contributes once at three or more distinct IDs, and Study Hall followed immediately by a training-tagged action contributes per adjacent pair, including across the bounded history's week boundary.
- Skill offers sort eligible definitions by stable-ID code units before unbiased integer weighted sampling without replacement. A valid three-card offer records at least three actual persisted RNG draws; failures, non-cadence weeks, paired-empty feature compatibility, pools below three, choices, and loadout edits consume none. One-sided catalogs fail instead of silently disabling the feature.
- M2 raw saves enforce offer/acquisition cadence weeks, strictly increasing acquisition weeks, contiguous offer indexes, non-overlapping plausible draw ranges, and unique ownership. Choosing fills only the first null slot; a full tuple is preserved, and explicit set/clear/replace commands are valid only during action planning.
- The M2 distribution baseline uses 64 checked-in literal seeds for paired film-repeat and weight-repeat strategies rather than discovering favorable seeds at runtime. It records exact per-seed offers, selections, RNG states, reload equivalence, and full skill/family/grade permille rates; robust direction assertions accompany exact configured-weight assertions.
- M2 build comparison first acquires Coverage Ledger and Recovery Window through ordinary cadence offers and choose commands, then derives both variants from the same round-tripped career using only planning-phase loadout commands. This keeps ownership, revision count, Body, action history, and RNG identical before the compared Film Study/Recovery week.
- The M2 Breakthrough phase is a single saved choose-one surface. Local radio selection never mutates CareerRun; confirmation runs one core command and blocks further commands until autosave succeeds. Returning to planning exposes the owned inventory and exact four-slot loadout in a collapsed detail surface so the weekly decision remains primary.
- M2 action cards visibly label catalog Body/GPA numbers as base changes before equipped skills. Contextual applied values and card/effect identity come only from persisted core result traces; week-end passive recovery uses a core-derived preview and retains the applied evidence after advance/reload. Phase title/pill selection is an exhaustive discriminated-union switch so future phases cannot silently masquerade as Breakthrough.
- M2 production E2E fixes the browser career seed through `crypto.randomUUID` before creation, then proves exact behavior-dependent offers and post-offer RNG from native IndexedDB rather than presentation inference. Korean and English each retain the Playwright project's native mobile/desktop viewport; the longer English copy also runs through a separate full 320×760 skill journey with touch/containment checks.
- Breakthrough choice uses deferred UI publication: the persisted offer remains the visible locked surface while the selected career is written or retried, and planning becomes visible only after successful persistence. Other already-legible weekly transitions retain their established optimistic-but-blocked presentation.
- M3 will make one domain/save jump to version 3 containing the full recruiting, roster, Practice Form, depth, and snap-projection state contract. Exact v1/v2 parsers remain supported; migrated in-flight phases finish before recruiting begins, and no placeholder program is assigned.
- M3 shortlists exactly five programs with zero RNG from persisted recruit/offer evidence. Only committing one offered program consumes career RNG to generate that program's seven-competitor WR room; unselected programs and rejected commands consume none.
- Until persistent program familiarity exists, M3 reveals every mechanically relevant offer fact. Depth uses fixed-point 45/20/15/10/10 talent/trust/form/scheme/readiness weights, a centralized one-rank hysteresis threshold, and content-owned monotone snap ranges.
