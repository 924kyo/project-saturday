# Save System

## Principle

M7.5 WR resolved-boundary staging retains the exact personal play and its post-resolution RNG separately from any following aggregate drive or pending opportunity. The continuation cursor and remaining-drive flag must be re-derived from that result, never trusted as independently editable state. Source-bound equality must reject missing/extra/undefined keys and sparse arrays, not merely compare lossy JSON serialization. This internal contract still requires a validated owning current-game source and explicit v8 career/session integration before a browser writer can publish it; historical v7 phases and readers are unchanged.

Save architecture is infrastructure from the beginning, not an export/import feature added later.

## Storage

For repeated WR careers, the live meta transport must use a lightweight canonical registry and independently authenticated alumni detail records, not repeatedly serialize/replay every prior career into one growing envelope. Preserve all old details and their original migration proofs. Registration validates the new alumnus plus lightweight ownership/index state; loading a specific history detail validates its own archive. Registry wire pages and each detail envelope remain below the existing one-million-byte cap. Session completion, new alumnus, registry pages/manifest and recovery snapshot must publish atomically; a failure retains the review and previous registry. Do not interpret a full-profile diagnostic's finite byte guard as permission to strand a later completed career.

The staged `wr_meta_manifest_v1` transport binds registry revision/header, entry/page counts and a constant-size checksum of the complete logical registry. Ordered `wr_meta_page_v1` envelopes contain at most 256 entries each, with matching revision/content/timestamps; only the last page may be short and an empty registry has no pages. All pages must reconstruct the exact canonical registry and its manifest checksum, so even same-revision page mixtures fail. Each `wr_alumni_detail_v1` envelope retains one literal strict legacy record or one source-replayed current record and must match its registry identity, schema and programs. Each envelope remains below 1,000,000 UTF-8 bytes; the aggregate logical index may grow beyond one envelope without dropping history. Checksums detect corruption, not hostile cryptographic tampering. The unselected codecs alone do not activate a writer or satisfy atomic storage/UI acceptance.

The staged v8 WR persistence facade now uses the same typed-codec engine as the unchanged shipping v7 facade. Retirement re-derives session/alumni/registry from the saved review under the shared lock and publishes all records in one cross-store transaction. Registry pages, shadow manifest, initialization marker and original legacy profile proofs use `migrationMetadata`; literal independent alumni details use `profile`. Normal index loading does not scan historical game details. Only obsolete derived registry pages are deleted in the successful transaction; alumni and original proofs remain. A valid shadow repairs a damaged primary manifest. Damaged/missing referenced pages fail closed; an initialized profile with both manifests missing cannot become an empty default. Retry is exact and idempotent, with no second registration or RNG/award. Current session recovery preserves original wire proofs, including colliding snapshot IDs and other positions' namespaces. This storage-only verification still requires coordinated frontend/Hub activation and the full required browser gate.

The staged v8 terminal completion retains its validated two-season review plus compact completion identity/content version; re-derive the entire completed career and alumnus from that source. Keep last-played season/off-field/world evidence as immutable terminal history and consume no RNG. `WrMetaProfileV2` is an explicit separate WR profile boundary with literal AlumniRecordV1 entries and source-archived two-season alumni; its v1 migration changes only the profile marker. Existing v1 readers/writers remain unchanged. Current session/meta publication must become one browser transaction with retry/recovery and original-proof preservation before activation. Four accumulated domain alumni have been profiled; repeated-career capacity/paging still requires verification, and no whole-envelope budget may be waived.

Staged WR v8 second-season review uses a required `wr_two_season_review_v1` source record and tagged review phase. Reconstruct the whole career (one review revision) and exact unchanged world from a strictly valid prior planning session; do not strip the current tag to use a legacy reader. The source cannot nest another current record. Preserve first-season summary/world evidence, current-season ledgers and both RNG streams, and verify season statistics sum to career totals. Retirement/meta needs its own explicit versioned terminal transition; this staged review does not enable a v8 browser writer or change any historical one-season record.

The staged v8 lifecycle bridge must validate a current completed game in full before acknowledgement. Only that explicit acknowledgement may create a private legacy-consumer input without the validated tactical retention tag/metadata; every actual numeric play, growth, total, RNG and world field remains unchanged. This is not a parser fallback, migration or v7 save. A successful advancing non-post-game result closes the same transient game-log boundary as the original lifecycle and clears the current record; any failure retains the original v8 record for exact retry. Cumulative football state must be identical across acknowledgement. Auxiliary meta/alumni outputs and all existing snapshots/history remain intact. General lifecycle commands cannot discard an active current game.

Current WR v8 staging distinguishes explicitly prepared new-game previews with a zero-draw retained tactical record and a `tactical_game_v1` phase tag. Neutral migrated previews have neither and finish through historical commands. Current parsing requires the owning mechanics catalog and compares the complete career to its source-replayed projection, including player/totals, phase, revision and career RNG. Current fields are not erased to satisfy a legacy validator. The session retains the existing strict world/linkage checks with world schema v1 and unchanged world RNG. These staged readers do not select a browser writer.

Staged WR tactical-game replay records retain one exact, strictly validated pre-kickoff source, ordered decisions and the current pending/resolved/post-game boundary. The source is the v7-compatible preview shape, which cannot contain another tactical record; no recursive current-game snapshots are allowed. Owning kickoff/drive/snap/completion functions must reconstruct the complete retained record, including source-derived growth and RNG. This current-only record is absent from neutral migration. Its own sub-1 MB guard does not replace the stricter whole-envelope budget or measured full-career gate. Historical games already in progress must finish under their original rules before new-game current activation.

Primary browser storage: IndexedDB via a thin typed adapter.

Recommended stores:

- profile/meta;
- current career;
- autosave snapshots;
- settings;
- migration metadata.

The settings store owns a separately versioned `onboarding-v1` preference with a canonical completed-topic list for Creation, Week, Team, and Skills. It is not gameplay state and does not increment CareerRun or save-envelope versions. Unknown versions, extra keys, duplicate topics, or unknown topics fall back to an incomplete default rather than being reinterpreted. Settings writes may update the UI optimistically but are serialized so later completion/replay choices cannot be overwritten by an older write; a storage failure never blocks gameplay.

Optional emergency mirror may use localStorage for a small latest-save envelope, not as the primary database.

## Save envelope

Conceptually:

```ts
interface SaveEnvelope<T> {
  saveVersion: number;
  contentVersion: string;
  createdAt: string;
  updatedAt: string;
  checksum: string;
  payload: T;
}
```

Exact checksum implementation is an engineering detail; it detects accidental corruption, not security tampering.

## Autosave

Autosave after verified domain transitions such as:

- completed weekly action;
- resolved event choice;
- post-game completion;
- skill-card choice;
- week/season transition;
- major offseason decision.

Avoid saving partial multi-step transactions as if complete.

## Snapshots

Keep rolling historical snapshots sufficient to recover from corruption/regression. Exact retention is tuneable; start around 20–60 lightweight snapshots depending size.

## Persistence request

The PWA may request browser persistent storage when supported, without blocking gameplay if unavailable.

## Migrations

Every schema change requires:

- incremented save version when structurally relevant;
- migration function;
- migration tests using previous-version fixtures;
- no silent field reinterpretation.
